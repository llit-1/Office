# Доставка и касса

## Доступ

| Название роли | Код роли | Доступ |
| --- | --- | --- |
| Доставка - Маркетинг | `MenuMarketing` | Категории и позиции меню, без стопов |
| Доставка - Запросы | `DeliveryRequests` | Страница запросов к Яндексу (заготовка) |
| Доставка - Админ | `MenuAdmin` | Меню доставки и запросы |
| Кассы - Аудитор | `MenuAuditor` | Стопы (аудит): глобальные стопы; сообщения на кассы. «Стопы (Яндекс)» не входят |
| Кассы - Обновление | `CashUpdate` | Вкладка «Обновление»: версии кассового клиента, установка и откат на кассах, удаление клиента |
| Кассы - Сотрудник | `Menu` | Только быстрые стопы для доступной торговой точки |

Права складываются: сотрудник с маркетинговой ролью видит оба раздела, но редактирование меню доступно только в «Доставке». Администратор доставки не получает доступ к кассам без отдельной кассовой роли.

При запуске сервера `DeliveryCashRoleInitializer` обновляет названия и описания существующих ролей и создаёт отсутствующие роли. ID и технические коды сохранены, существующие назначения группам не меняются. Новые роли `DeliveryRequests` и `CashUpdate` необходимо назначить нужным группам через управление пользователями. Инициализатор не назначает их автоматически: аудитор без `CashUpdate` вкладку «Обновление» не видит.

## Маршруты

- `/Delivery`: вкладки доставки с автоматически открытым меню (для роли только «Запросы» — запросами); `/Delivery/menu/:groupId?`: меню; `/Delivery/requests`: запросы.
- `/Cash`: вкладки кассы с автоматически открытыми быстрыми стопами; `/Cash/items/:groupId?`: быстрые стопы; `/Cash/stops`: глобальные стопы; `/Cash/messages`: сообщения; `/Cash/update`: версии кассового клиента.
- Старые `/DeliveryMenu` и `/DeliveryMenu/stops` перенаправляют в новые разделы с учётом ролей.

Оба раздела используют общий `TabNavigation`. Вкладки сохраняются при переходах и открытии категории; URL отражает выбранную страницу и работает при прямом входе. Компоненты вкладок входят в загрузку раздела, поэтому его предзагрузка также загружает компоненты страниц. Данные получает только открытая вкладка.

Быстрые стопы сохраняют прежнюю семантику: уровень 2, только агрегаторы, до ближайших 00:00 по Москве. Глобальные стопы уровня 1 блокируют кассы и агрегаторы. Снять глобальную блокировку можно через «Стоп-листы».

В быстрых стопах поиск охватывает все активные категории (название, описание, RK-код); позиции загружаются при первом запросе, не более четырёх категорий одновременно. В результатах указана категория. Карточки явно показывают доступность, быстрый или глобальный стоп и торговую точку. В меню доставки отмечена активность категорий и позиций.

Обе страницы стопов обновляют данные каждые 30 секунд и при возвращении в видимую вкладку/окно. Время действия проверяется каждую секунду без сетевого запроса; завершённые стопы перестают блокировать позиции и исчезают из текущего списка. Ошибка фонового обновления не скрывает страницу; быстрые действия временно отключаются до успешного обновления.

Выбор точки аудитора сохраняется в localStorage отдельно для каждого пользователя и проверяется по доступным точкам при загрузке. Сотрудникам сохранённый выбор аудитора не применяется. Панель точки закреплена над каталогом, имя точки также показано на карточке и в подтверждении. Перед изменением стопа повторно проверяется его состояние; при внешнем изменении действие отменяется с уведомлением, без подмены подтверждённой операции.

## Сообщения

Клиент отправляет `POST /api/Cash/messages` с `{ "location": "<GUID>", "message": "<текст>" }`. Сервер проверяет роль аудитора, текст и наличие активной торговой точки с RK-кодом, затем вызывает `POST https://yeapi.ludilove.ru/Message/send` с теми же полями. Контракт проверен по [Swagger](https://yeapi.ludilove.ru/swagger/index.html).

Адрес можно переопределить через `DeliveryMenuApi:MessageUrl`. Список получателей (`GET /api/Cash/locations`) Office берёт из yeapi `GET /api/cash/getlocations` — тот же список, из которого кассы выбирают точку при установке; остаются только актуальные точки (`actual = 1`), отсортированные по названию. Перед отправкой точка проверяется по этому же списку. Успешный HTTP-ответ означает принятие запроса сервисом; подтверждение показа сообщения на кассе контрактом не предусмотрено. Автоматического повторения отправки нет.

## Обновление касс

На вкладке «Обновление» аудитор ведёт версии кассового клиента (выбор, скачивание, загрузка, удаление архива), раскатывает выбранную версию на все кассы или на одну, удаляет клиент с конкретной кассы и видит, на каком этапе каждая касса.

Сервер проксирует запросы к yeapi и не хранит архивы сам:

| Office | yeapi | Назначение |
| --- | --- | --- |
| `GET /api/Cash/versions` | `GET /api/cash/versions` | Список версий |
| `POST /api/Cash/versions` | `POST /api/cash/versions` | Загрузка архива (`multipart/form-data`: `file`, `version`, `actual`) |
| `DELETE /api/Cash/versions/{id}` | `DELETE /api/cash/versions/{id}` | Удаление версии |
| `GET /api/Cash/versions/{id}/download` | `GET /api/cash/versions/{id}/download` | Выгрузка архива |
| `GET /api/Cash/clients` | `GET /api/cash/getcashclients` | Список касс |
| `GET /api/Cash/clients/tasks` | `GET /api/cash/task/{cashId}` на каждую кассу | Последняя задача и её этап |
| `POST /api/Cash/versions/{id}/install` | `POST /api/cash/task?cashId=…&type=Update&versionId={id}` на каждую кассу | Установка выбранной версии на все кассы |
| `POST /api/Cash/clients/{cashId}/install?versionId=` | `POST /api/cash/task?cashId=…&type=Update&versionId=…` | Обновление одной кассы |
| `POST /api/Cash/clients/{cashId}/delete` | `POST /api/cash/task?cashId=…&type=Delete` | Полное удаление клиента с кассы |

Адрес переопределяется через `DeliveryMenuApi:CashUrl`, типы задач — через `DeliveryMenuApi:CashUpdateTaskType` (`Update`) и `DeliveryMenuApi:CashDeleteTaskType` (`Delete`). yeapi принимает только `Install`, `Update`, `Delete` с заглавной буквы. POST задачи уходит с пустым телом: IIS перед yeapi отвечает 411 на POST без `Content-Length`. Текст отказа yeapi («Касса не найдена.» и т. п.) передаётся в уведомление.

Номер версии проверяется и на клиенте, и на сервере (цифры через точку, например `1.4.8.0`), формат файла — только zip, предельный размер загрузки — 256 МБ. Контракт `GET /api/cash/versions` в swagger не описан, поэтому сервер разбирает ответ без учёта регистра полей и по синонимам и приводит к `{ id, version, actual, createdAt, size }`.

### Как касса выполняет задачу

Задачу забирает RKNet_CashMonitor на кассе: сразу по SignalR-сигналу, который yeapi шлёт клиенту в группу `cash:{cashId}` (`CashUpdate(versionId, taskId)` и `CashDelete(taskId)`; клиент передаёт задачу монитору), или при опросе `GET task/{cashId}` раз в 5 минут. `GET task/{cashId}` отдаёт последнюю задачу со stage не `Completed`. В `PUT task/{id}/stage` он пишет **последний успешно выполненный шаг** — после того, как шаг удался:

- **Update/Install:** `Downloading` → `StoppingClient` → `DeleteOldVersion` → `Extracting` → `Configuring` → `Completed`. Без `versionId` касса ставит самую свежую версию с `actual`. Выбранная ТТ, cashId и принтер переносятся в новую версию.
- **Delete:** `StoppingClient` → `DeleteOldVersion` → `Ending_installer`, затем монитор вызывает `POST task/delete-installer` (ответа не ждёт: через 10 секунд сервер ставит `Delete_installer`, удаляет папку `CashPath` на кассе и саму кассу из базы, после чего пишет `Completed`) и удаляет себя. Портал считает `Delete_installer` завершённым удалением.
- Статуса ошибки нет. Упавший шаг монитор повторяет (паузы 10 с, 30 с, 1 мин, 2 мин); если не помогло — ждёт 30 минут и продолжает с того же шага. Последний удавшийся шаг и версия задачи хранятся ещё и в `monitor_state.json`, поэтому задача продолжается и после перезагрузки кассы.

### Интерфейс

Панель: поиск по ТТ, IP и версии, селект версии, «Установить на все кассы», «Добавить версию», скачивание и удаление архива, фильтры «Все / Отстают / В работе / Без связи», «Обновить». Плитки: всего касс, отстают, в работе, без связи. В селекте только номера версий, без пометок. «Актуальной» считается самая свежая версия с `actual` — именно её кассы ставят по умолчанию; удалить версию с `actual` нельзя.

`getcashclients` присылает установленную версию числом `cashVersion` — это id из списка версий; Office отдаёт его как `cashVersionId`, а номер (`version`) подставляет страница. Если версии с таким id в списке уже нет, на карточке прочерк «—», и касса считается отстающей. Пока список версий не загружен, вместо номера «…» и отставание не считается. Строковое значение `cashVersion` принимается как номер версии.

Карточка кассы: ТТ, IP, последняя связь, установленная версия и две кнопки — «установить версию» и «удалить клиент» (с подтверждением). «Установить версию» открывает окно с текущей версией кассы и выбором любой загруженной версии (по умолчанию — выбранная в панели); кнопка подписана «Обновить», «Откатить» или «Переустановить» по сравнению номеров, при откате выводится предупреждение. Так любую кассу можно откатить на конкретную версию. Селект версии в панели — той же высоты, что остальные контролы, и узкий. Если у кассы есть задача, на карточке блок с названием («Обновление до 1.3», «Удаление»), шагом, который касса выполняет сейчас (следующий за записанным), счётчиком «N из M» выполненных шагов и полоской сегментов. Задача без записанного шага показывается как «Ожидает кассу» — это и очередь, и первый шаг в работе. Завершённая задача показывает «Обновлено» / «Установлено» / «Клиент удалён». Пока задача в работе, кнопки кассы выключены. Цвет карточки — по версии: зелёная — актуальная, жёлтая — отстала, серая — касса не сообщила версию.

Пока хотя бы одна касса в работе, список касс и этапы перечитываются каждые 3 секунды, без спиннера. Ошибка чтения этапов не скрывает кассы, ошибка списка версий не скрывает кассы и наоборот. `GET task/{cashId}` отдаёт только незавершённую задачу — объект `{ id, cashId, type, stage, cashVersionId, stageChanged }` (проверено вживую), начальный этап `Created`; после завершения ответ 404. Office читает `cashVersionId` как версию задачи (массив тоже принимается, берётся задача с наибольшим id). Раз завершённую задачу сервис не отдаёт, страница показывает итог («Обновлено» / «Клиент удалён») для задачи, которая была в работе и пропала из ответа, — до следующего действия с кассой. Обновление по локальной сети занимает секунды, поэтому во время работы опрос идёт каждые 3 секунды, и промежуточные этапы можно не застать.

Новая версия загружается с `actual=1`: она сразу становится версией по умолчанию для новых установок и задач без `versionId`. Задач уже работающим кассам загрузка не ставит — для этого «Установить на все кассы» или кнопка на карточке.

Частичный успех раскатки не считается ошибкой: интерфейс показывает, сколько касс приняли задачу и какие нет.

## Проверка

`npm test` в `office.client`, `npm run build` и `dotnet build Office.Server/Office.Server.csproj -p:BuildProjectReferences=false`.

Тесты проверяют направления по ролям, ограничения прямого доступа, совмещённые роли, отсутствие редактирования в кассе и стопов в доставке, обработку отправки сообщений и ошибок. Вкладка обновления покрыта отдельно: выбор актуальной версии, запрет удаления раздаваемой версии, удаление архивной с подтверждением, проверка номера и формата файла, повтор неудачной загрузки списка, скачивание и сохранение формы после ошибки; для раскатки — подтверждение перед установкой, установка именно выбранной версии, честный отчёт о частичном успехе и отсутствие автоустановки после загрузки; для задач — текущий шаг и счётчик на карточке, «Ожидает кассу», завершённая задача, шаги удаления, блокировка кнопок, опрос только во время работы, удаление клиента с подтверждением и текст отказа; для карточек касс — вывод карточек, пометка отставших версий, отказ от пометки без списка версий, счётчики по состояниям, фильтр «Отстают», обновление одной кассы из карточки, независимость блоков при сбое и обновление списка по кнопке. Серверные тесты `CashControllerTests` проверяют разбор `getcashclients` (числовой `cashVersion`), задач и ошибок yeapi, типы `Update`/`Delete`, передачу `versionId` и пустое тело POST. Проверки используют подмену API и не обращаются к yeapi.
